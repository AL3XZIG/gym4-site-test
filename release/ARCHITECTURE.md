# Архитектура v4

## Цель

Сделать единый сайт гимназии с серверной CMS, публичной витриной, редакционными ролями и отдельным модулем выборов. Демо v0.3 остаётся доступным до приёмки v4.

## Целевая схема

```
Посетитель / Редактор
        |
      HTTPS
        |
   Nginx / reverse proxy
        |
     Django
      |  |
      |  +-- Public views / templates / JSON API
      |
      +-- CMS: pages, news, documents, menus, settings, media
      |
      +-- Elections: existing module after audit
        |
    PostgreSQL
        |
  persistent media storage
```

## Технологии

- Django 5.2 (текущая база проекта; версию обновлять только после проверки совместимости).
- PostgreSQL 16.
- Django templates + progressive enhancement на vanilla JS; SPA не требуется.
- Gunicorn за Nginx.
- Docker Compose для воспроизводимого окружения.
- Playwright для браузерных E2E; pytest/Django TestCase для backend.
- GitHub Actions для линтинга, тестов, сборки и проверки артефакта.

Не вводить React/Vue, Redis, Celery или отдельный поисковый движок без измеримой необходимости. Для первой версии предпочтительнее простая архитектура с меньшим числом сервисов.

## Принципы

1. **Единый источник данных.** Публичные страницы, меню и новости получают опубликованные данные из CMS.
2. **Сервер — источник истины.** localStorage допустим для UI-предпочтений, но не для контента, авторизации или голосов.
3. **Черновики не публичны.** Публичные views/API возвращают только опубликованные объекты.
4. **Безопасность по умолчанию.** CSRF, escaping шаблонов, безопасная загрузка файлов, rate limiting и минимальные права.
5. **Доступность встроена.** Семантическая HTML-структура, focus states, skip link, reduced motion, контраст и понятные ошибки.
6. **Никаких фиктивных функций.** Если отправка формы, поиск или редактор не подключены к серверу, UI прямо обозначает ограничение.
7. **Демо отделено от production.** Тестовые профили, фиктивные контакты и демо-голосование не попадают в production.
8. **Обратная совместимость URL.** Старые адреса сохраняются либо перенаправляются.

## Предлагаемая структура

```
release/
  README.md
  PLAN.md
  ARCHITECTURE.md
  DATA_MODEL.md
  QA.md
  STATUS.md
  decisions/
  frontend/
    templates/
    static/
  backend/
    config/
    apps/
      core/
      pages/
      news/
      documents/
      media/
      elections/   # интеграция существующего server/ после аудита
  tests/
    unit/
    integration/
    e2e/
  scripts/
```

Это целевая структура рабочей зоны. Не копировать `server/` в `release/backend/apps/elections/` до аудита импортов, миграций, моделей и тестов.

## Контуры приложения

### Публичный контур
- только опубликованные страницы и записи;
- публичный поиск;
- доступные документы с метаданными;
- публичные JSON endpoints только при необходимости;
- никакой выдачи черновиков, внутренних заметок и персональных данных.

### Редакторский контур
- аутентификация и роли;
- создание/редактирование черновиков;
- предпросмотр до публикации;
- согласование и публикация;
- история изменений и аудит;
- управление медиа и меню.

### Контур выборов
- изолированная область прав и данных;
- существующие роли кандидата, модератора и организатора после проверки;
- отдельная модерация материалов;
- никакого включения электронного голосования без отдельного threat model и утверждённого регламента.

## Сборка и публикация

- `main` сохраняет v0.3 до завершения v4.
- `v4-release-work` — текущая рабочая ветка подготовки.
- Сначала CI собирает тестовую сборку v4 из `release/`.
- Публичная сборка должна иметь allowlist файлов, а не копировать весь репозиторий.
- Перед переключением выполнить smoke tests, проверить redirects и иметь план rollback.
- GitHub Pages не должен публиковать backend, секреты, черновики или редакторские интерфейсы.

## Границы

Эта архитектура — целевая спецификация. Наличие документа не означает, что CMS, E2E, серверная сборка или production deployment уже реализованы.
