# Целевая архитектура сайта гимназии

**Статус:** часть серверного контура реализована для выборов президента гимназии (Django, PostgreSQL, Docker Compose, VPS installer, роли и модерация). Полная CMS официального сайта, документы и остальные разделы пока остаются статическими. Цель — единая система, которую системный администратор может развернуть, а сотрудники — обновлять через браузерную панель.

## 1. Два независимых контура

| Контур | Назначение | Стек | Размещение |
|---|---|---|---|
| Demo | Показ дизайна, навигации и интерактивности | HTML, CSS, vanilla JS | GitHub Pages |
| Production | Официальный сайт, документы, новости, редактура | Django, PostgreSQL, Django Admin, Gunicorn, Nginx, Docker Compose | Согласованный сервер/VPS |

GitHub Pages — только статическая витрина. Текущий демонстрационный проект использует самостоятельные HTML-файлы и не требует Python-генератора, сборщика или runtime-backend. Она не принимает обращения, не хранит персональные данные и не является источником официальных сведений.

## 2. Рекомендуемый production stack

- **Django LTS:** маршрутизация, шаблоны, ORM, аутентификация, CSRF и административная панель.
- **PostgreSQL:** новости, страницы, документы и настройки.
- **Django Admin:** редактирование контента сотрудниками без доступа к Git, shell или SQL.
- **Gunicorn:** WSGI application server.
- **Nginx:** HTTPS/reverse proxy, раздача static files, проксирование и ограничения размера запросов.
- **Docker Compose:** воспроизводимый запуск web + db; Nginx устанавливается на хосте и проксирует запросы. БД и media хранятся постоянно.
- **Django templates + CSS/JS:** без отдельного React/Vue SPA на первом этапе — меньше компонентов и проще сопровождение.

Wagtail можно рассмотреть позднее, если потребуется визуальный редактор страниц и workflow согласования. Для первой версии Django Admin проще в эксплуатации.

## 3. Реализованный модуль выборов

Каталог `server/` содержит отдельное Django-приложение кампании. В нём есть роли `organizer`, `moderator`, `candidate`, связь пользователя с карточкой кандидата, черновики материалов, очередь модерации, публичный JSON API и журнал действий. Кандидат видит и меняет только собственные черновики; публичный API отдаёт только одобренные записи. Файлы хранятся вне публичного webroot и выдаются через проверку статуса публикации. Самостоятельной регистрации нет.

`deploy/` содержит Docker Compose, Nginx-шаблон, установщик, обновление и резервное копирование. VPS раздаёт отдельную сборку `public/`, куда не попадают исходники сервера, `.env`, локальные редакторы и документация. GitHub Pages остаётся независимой демоверсией; на VPS страница выборов и лента новостей получают одобренные материалы через API.

Электронный бюллетень не входит в реализованный модуль: отсутствуют проверка избирателей, одноразовые допуски, тайна голоса, защита от повторного голосования и подсчёт. Не включать голосование до отдельного проектирования и утверждения регламента.

## 4. Поток запросов

Посетитель или редактор → Nginx/HTTPS → Gunicorn → Django → PostgreSQL. Nginx отдаёт static files; документы хранятся отдельно в media. Редактор работает через Django Admin. Резервное копирование охватывает БД и media.

## 5. Структура production-кода

    production/
      manage.py
      config/settings/
        base.py
        development.py
        production.py
      config/urls.py
      apps/
        core/          # настройки сайта и общие компоненты
        pages/         # информационные страницы
        news/          # новости и публикация
        documents/     # документы и версии файлов
        admissions/    # сведения о приёме
        feedback/      # обращения после правового согласования
      templates/
      static/
      media/
    Dockerfile
    docker-compose.yml
    deploy/nginx/default.conf
    .env.example

Это целевая структура полной CMS; фактический модуль выборов расположен в `server/` и имеет отдельную упрощённую структуру.

## 6. Модели данных

| Модель | Поля и назначение |
|---|---|
| SiteSettings | название, адрес, телефоны, e-mail, часы работы, внешние ссылки |
| Page | slug, title, body, status, updated_at, SEO title/description |
| NewsItem | title, slug, summary, body, image, published_at, status, category |
| Document | title, category, file, document_date, version, is_published |
| MenuItem | label, url, parent, position, is_active |
| ContactMessage | тема, текст, дата, статус обработки — только при утверждённом процессе |

Публичные документы должны иметь понятные названия, дату/версию и доступные ссылки. Не публиковать внутренние документы с персональными данными.

## 7. Роли

- **Системный администратор:** развёртывание, обновления, backups, учётные записи.
- **Главный редактор:** публикация/снятие материалов, управление страницами.
- **Редактор:** черновики и правки без управления пользователями и настройками.
- **Посетитель:** чтение опубликованного контента.

## 8. Безопасность и эксплуатация

1. Секреты — только в переменных окружения; .env не коммитить. В Git хранить только .env.example.
2. DEBUG=False, отдельный SECRET_KEY, ограниченные ALLOWED_HOSTS, корректный CSRF_TRUSTED_ORIGINS, secure cookies и HTTPS.
3. PostgreSQL не публиковать в интернет; отдельный пользователь БД с минимальными правами.
4. Запуск приложения от непривилегированного пользователя.
5. Ограничить тип и размер загружаемых файлов; проверять расширение и фактический формат; не исполнять загруженные файлы.
6. Для форм определить законное основание, уведомление/согласие, срок хранения, ответственного и процедуру удаления. Добавить rate limiting и антиспам.
7. Не записывать пароли, токены и полные тексты обращений в логи без необходимости.
8. Ежедневный резервный дамп БД и копия media, ротация, хранение вне основного сервера; регулярно проверять восстановление.
9. Обновлять зависимости и базовый образ; фиксировать версии и проверять миграции до выкладки.

## 9. URL и обязательные разделы

- Сохранить адрес раздела /sveden/ и его подразделов.
- Составить карту старых URL gym4.net и настроить 301 redirects, где возможно.
- Не удалять документы и исторические материалы без решения администрации.
- Структуру раздела сведений сверить с действующими требованиями РФ непосредственно перед запуском. Наличие красивой страницы само по себе не означает соответствие требованиям.
- Проверить доступность с мобильных устройств, клавиатуры и экранного диктора; обеспечить читаемые PDF и понятные подписи ссылок.

## 10. План реализации

1. Согласовать реквизиты, документы, контакты, новости, фотографии и ответственного редактора.
2. Утвердить дизайн и навигацию по GitHub Pages demo.
3. Создать Django-проект, модели, роли, админку и шаблоны.
4. Перенести проверенный контент и документы, настроить redirects.
5. Поднять Docker Compose, Nginx, HTTPS, persistent volumes, backups и monitoring.
6. Провести приёмку: тесты, ссылки, доступность, восстановление и редакционный процесс.
7. Передать инструкции sysadmin и редактору, схему восстановления и список ответственных.

## 11. Критерии готовности

- Контент редактируется через браузерную админку.
- Черновики отделены от опубликованных материалов.
- Обязательные сведения и документы подтверждены владельцем сайта.
- HTTPS, резервное копирование и проверенное восстановление настроены.
- Секреты отсутствуют в Git; БД недоступна извне.
- Старые URL сохранены или перенаправлены.
- Есть инструкции для администратора и редактора.

**Граница текущего этапа:** backend выборов — подготовленный MVP, который всё ещё требует развёртывания на отдельном VPS, HTTPS, настройки пользователей, проверки восстановления резервных копий и приёмочных испытаний. Полная CMS сайта и реальное электронное голосование не реализованы. Реальные данные и юридические тексты должны быть согласованы до публикации.
